# Security: threat model

Philobiblos holds a household's reading, its kids' profiles and a delivery address (never the bookshop card number), and reads mail,
shared posts, PDFs, videos and web pages it did not write. Security comes before polish and features (ADR 0009).

## Assets

| Asset | Where | Why it matters |
|---|---|---|
| People, kids' names and birth years, reading and takeaways | SQLite | private to the household; kids especially |
| Delivery address, the bookshop's address | `sealed_secret` (AES-256-GCM, bound to its name), key outside the database: `PHILOBIBLOS_SEALING_KEY` or `PHILOBIBLOS_SEALING_KEY_FILE`; standalone makes `sealing.key` (0600) in its own folder, `PHILOBIBLOS_KEYS_DIR` (`./keys` next to `./data` in docker-compose.yml), never inside the data folder | physical address; where orders go |
| IMAP app password of the Philobiblos-only mailbox | secret (env/file) | reads the bookshop's mail |
| SMTP password (optional, off by default; ADR 0011) | secret (env/file), never in SQLite | sends mail as that account; Philobiblos uses it for join codes only |
| Join links, join codes, waiting people | links as SHA-256; codes as an HMAC keyed by a key derived from the sealing key with HKDF-SHA-256 (`info = "join-code"`), outside the database; waiting people's names, passkeys and the address being verified in SQLite, the address deleted once the request is decided or lapses (an accepted person keeps only the domain that matched) | a link lets strangers ask to join; a code proves an address that a rule accepts automatically |
| Claude API key (if opted in) | `sealed_secret` (`claude_api_key`), sealed like the delivery address with the same key outside the database; entered by an admin in Settings, write-only | costs money, sends data out |
| Web Push's application server key (VAPID, P-256) | `sealed_secret` (`vapid_private_key`), sealed like the delivery address, made on the first need; only its public half is answered (`GET /push/key`) | whoever holds it can push to every device the household added |
| Push subscriptions (each device's endpoint and keys) | `push_subscription`, per person | an endpoint with the key lets a sender reach that device |
| Share tokens | hashed in `share_token` | anyone holding one can drop shares into a person's Inbox |
| The server itself | container | a foothold on the home network |

## Actors and what stops them

| Actor | Could try | Controls |
|---|---|---|
| **A household adult** | read another adult's takeaways, change their settings, add or remove people | per-person routes act on the signed-in person (readings: your own, and kids', for whom adults act); a takeaway is sent only to its own person and to no AI unless that person turns on `takeawaysToAi` (`library/ai-context.ts`), and a link or idea the AI wrote from it (`private_to`) shows its reason, and is decided, only by that person; for anyone else it answers 404 like a missing one, so not even its existence shows (`knowledge/knowledge.ts`); shared data (budget, backlog) is shared by design; admins manage people; the last admin cannot be removed or demoted |
| **A kid** | sign in, change picks or feedback | `audience: adults`: kids have no access; adults act for them |
| **Whoever holds a join link** (forwarded, posted, leaked; ADR 0011, planned: philobiblos#34) | join, become an admin, fill the waiting list, learn whether a link or a person exists, see household data, pass as a family member to get approved | standalone only (under HomersLab every join route answers 404); the token in the `#fragment`, kept as SHA-256, made with a fresh sign-in; 7 days and 5 uses by default, revocable, revoked with its admin; by default it opens only from the household's networks and everyone waits for an admin, and with no network listed no link can be made (an empty list never means anywhere); a use counts at the passkey's enrolment, in the same transaction; at most 10 people wait in a household, and a waiting person reaches one page and no household data (403 everywhere else), with nothing they add stored; a decline or 7 days deletes them and their passkey; every approval and every decline needs an admin's fresh sign-in (under HomersLab the edge's recent sign-in signal, ArjunRachithcf/homeward#253, and refused without it), and only an admin's choice makes an admin; the waiting list shows each person's link, time, whether they came from the household's networks and any verified address, so a typed family name alone is never the reason to approve; a name that matches a member's gets the same answer as any other (no "name taken"); opening, joining and asking for a code are rate limited per address and per link; an unknown, expired, revoked, used-up or out-of-network link gets the same answer |
| **Whoever tries a join rule** (an address at the household's domain, a guess at the code, a forged address or network) | be accepted automatically, as an admin; brute-force the code; learn which addresses are members; make Philobiblos mail anyone, or many | rules only narrow (a link's rules add to the household's) and a match accepts an adult, never an admin; the mail domain needs a verified address: standalone a 6-digit code (random, 10 minutes, 5 tries, one live code an address, bound to the join request that asked for it so it works from no other link or browser, compared in constant time, kept as an HMAC with a key derived from the sealing key (HKDF-SHA-256, `info = "join-code"`), so a copy of the database cannot try the million codes), under HomersLab only `X-HomersLab-Email` from the edge, which sets it only for an address its sign-in verified and strips a client's (ArjunRachithcf/homeward#248); sending is limited per address (3 an hour, 10 a day: 50 tries a day), per join link (10 a day) and per household (30 a day), so made-up addresses at the domain still get at most 150 tries a day against a household; the SMTP host is in the egress list only when set, and its client is the one outgoing mail connection (an architecture test); the answer is the same whether or not a mail went out (no match, a member's address, a full list); the recipient is one plain address, the only one (no line breaks, commas or display names), the mail fixed text holding the code alone, over TLS with the certificate verified; a public mail provider's domain cannot accept automatically; location is the household's networks only (no GPS, no geolocation), the client address the connection's or, only from `PHILOBIBLOS_TRUSTED_PROXY`, the forwarded one |
| **A HomersLab person not yet approved** | use Philobiblos because the edge let them through; keep a role Homeward took away; gain one Homeward gave | each person the edge sends for the first time waits for a Philobiblos admin, except Homeward admins (approved as admins); the Philobiblos role is never above the Homeward role and is lowered at the next request after a demotion; a removed person no longer arrives, and is marked removed when the household provider reports it; until then admin-only pushes (`join`) carry their kind alone and acting on one is a request the ceiling applies to, and a removal or demotion seen deletes their admin-only subscriptions; a Homeward promotion never raises a Philobiblos role by itself |
| **A stranger on the LAN** | reach the app, forge `X-HomersLab-Person`, guess a sign-in | standalone binds `127.0.0.1` by default; in homerslab mode the headers count only from the configured proxy address, and only once HomersLab's edge strips and sets them (`PHILOBIBLOS_EDGE_IDENTITY`, HomersLab #236) and its per-app firewall (HomersLab ADR 0020) lets only the edge reach Philobiblos; passkeys only, nothing to guess; sign-in steps rate limited; setup and invite links one-time, hashed, in the fragment (ADR 0010) |
| **A stranger on the internet** | the same, through whatever exposes Philobiblos | Philobiblos is never public by itself (`public: false`); HomersLab's proxy and sign-in are in front |
| **Whoever holds a share token** (lost phone, leaked Shortcut) | post shares; read anything; guess a token; keep the household's Shortcuts out | write-only to `POST /api/shares` (every other route answers 401 to it, and a request with `Authorization: Bearer` is judged by the token alone, never by a cookie next to it); a token is its row's id and 256 random bits, kept as SHA-256 only, the hashes compared in constant time (`timingSafeEqual`, against a dummy when no row has that id), shown once (with its QR code) and never again; revocable in Settings, at most 10 live a person, its person's own (a person who becomes a kid loses theirs; M0's tokens, which had no id, were revoked by migration 0008); the token is looked up first and a valid one always passes, so wrong ones cannot lock anyone out: they are counted per address and per the token id they name, and past 10 in 10 minutes a wrong one is answered 429; 30 shares a person per 10 minutes; at most 2 uploads open at once a person (session and tokens together, under 6 for the household), each cut after 15 s without a byte or 5 minutes in all, and a token's open uploads cut the moment it is revoked, so a held token blocks only its own person's two slots, and only while it keeps sending |
| **Hostile mail** (spoofed "bookshop" mail, a forwarded phishing mail) | fake quotes or invoices, links to click, malicious PDFs, MIME bombs, using Philobiblos's DNS | the Philobiblos-only mailbox over IMAP (`net/imap.ts`): TLS on 993 from the first byte, certificate and name verified, TLS 1.2+, the folder opened with EXAMINE and messages read with BODY.PEEK (nothing flagged, moved or deleted; an architecture test keeps it so), the password a secret never in a log or job_run; each mail once (`mail_seen` by Message-ID, `mail_cursor` by UID); before any effect the From (one address) and Sender must be at exactly one of an enabled connector's mail domains (none enabled: no mail counts), the mail addressed to the household (`PHILOBIBLOS_MAIL_RECIPIENTS`), each single-instance header present once, and its aligned DKIM, by exactly one of that connector's signing domains, must verify over the whole body (no `l=`) and every header Philobiblos reads, or a trusted provider's ARC seal (`PHILOBIBLOS_MAIL_ARC_SEALERS`, none by default) must vouch dkim=pass for one of those signing domains, aligned with the From as well, under the same coverage rules; only a verified mail claims its Message-ID; DNS only for DKIM key records, a few per mail; unverified mail changes nothing and none of its content is kept; the header block strict RFC 5322 (a line a parser cannot read would turn the signed headers into body) and what the MIME parser read equal to the verified headers; 25 MB per mail, MIME depth 8, 64 parts, 256 KB of headers, no nested messages parsed; links never followed, nothing fetched; **no mail text is stored**: a verified mail keeps its ids, date, subject, PDF count and mailbox position, and the parsers keep only structured fields, each string field (the ids too) dropped if it holds a piece of the sealed delivery address (a line, a comma part or a word of 5+ letters; diacritics, ue/oe/ae and `…str.` folded) or a run of 12+ digits (any separators, after NFKC, format characters stripped); the header block also refuses control characters, white-space-only continuations and encoded words in names. **The parsers** (`mail/parse.ts`, `mail/effects.ts`): effects apply only to a mail `openVerified` produced (`applyMail` refuses any other object), and a mail is read again from the mailbox only by its kept UID under the same UIDVALIDITY, only if the signed Message-ID there is the same, and through every check again; the kind comes from signed headers only, with the mail's own connector's words (quotes only from its quote senders); the household's quoted request is never read (nothing after a reply marker, no `>` line); each parser bounded (5,000 lines, 1,000 characters a line, 100 books, 1 MB) and linear, and fails closed with its version stamp on any layout it does not know (an amount it cannot place, a book without price or status, a row that does not read whole, a total that is not the sum, a PDF cut short), changing nothing; effects touch only Philobiblos's own records (order lines, the order's total and status, copies, prices), on composed orders only (drafted or quoted, tied by the signed Subject's month or In-Reply-To), never people, settings or mail; an invoice number counts once; lines that match no book or several go to the Inbox; the invoice PDF's rows come only from the media worker and are never stored; a PDF the worker cannot read is tried 5 times, then given up |
| **A hostile share** (image, video, caption) | exploit an image/video decoder; prompt injection in a caption; make another site post a share (CSRF); fill the disk | `POST /api/shares` (`shares/shares.ts`): with a session only from Philobiblos's own Origin; the PWA's share target lands in its service worker (`apps/web/public/sw.js`), which intercepts that one POST and nothing else and keeps the parts (bounded: fields, 30 files, any past them left out and counted, each within its type's limit, told from its first bytes, and 100 MB together; a file over it is left out on its own, so one large photo never fails the share) in the browser's cache, and the share screen, Philobiblos's own page, shows what arrived and posts it only when the person taps "Send to the Inbox" (any site can make a browser POST to the share target, and the worker cannot tell a share sheet from another site, so the tap is the line; an untouched share expires after an hour, and a newer one replaces it); a share-target POST that reaches the server, before the worker is installed, is answered with a redirect and not read; 30 files, an image up to 20 MB, a video up to 64 MB, 100 MB a share together, each file streamed to its staging file as it arrives with a running count (past a limit the rest is read and dropped and the file deleted; nothing is held whole in memory), at most 2 uploads read at once a person and 6 for the household (429 beyond), each cut (the request destroyed, its slot freed, its staged files deleted) after 15 s without a byte, after 5 minutes in all (and no request lasts past 6: `requestTimeout`), or when the token it came with is revoked, 10 fields, each field bounded (2,000 to 5,000 characters, control characters stripped); a file's type from its first bytes (JPEG, PNG, WebP, GIF, each with its whole fixed header: a JPEG's first marker segment, a PNG's IHDR, a WebP's first chunk, a GIF's screen descriptor; MP4/MOV and WebM by their `ftyp` brand or EBML DocType; never its name or claimed type; a HEIC, an HLS playlist or anything else is refused, 415, and nothing is kept); staged in the server's own `data/incoming/<share>` (0700, never served) and each original deleted as soon as the media worker has answered for it, whatever it answered; only the worker's re-encoded JPEGs are kept (an image's, or a video's frames: see "A hostile video") (`data/shares/<share>`); without a worker (HomersLab before it runs one) files are refused (503), the link and caption still taken; a worker down for a day fails the share and deletes what waited. A link is kept as text (http(s) without credentials) and never fetched or made clickable (ADR 0006). A share is its sharer's alone: anyone else gets 404 for it in `GET /shares/{id}` and the Inbox, so what the AI finds in it, which may rest on that person's takeaways (`private_to`), never shows to another adult. The media worker: its own container (`philobiblos-worker`) as its own user (`PHILOBIBLOS_WORKER_UID`, default 61000; it refuses to start as root or as the folder's owner) with `network_mode: none`, a read-only root, no capabilities, no-new-privileges, 768 MB and 64 processes; it sees only `work/in` (read-only) and `work/out` (which it cannot replace: its parent is the image's read-only `/work`), never the database or the keys; one job at a time, each in a child process (its own process group, killed with its result or at 20 s, a video at 60 s; after each job the worker looks in `/proc` for any other process of its user, one that escaped the group with a session of its own, and if there is one the job fails and the worker exits, so Docker restarts the container and its PID namespace with everything in it) with a 256 MB JavaScript heap (ArrayBuffers and libvips' memory are bounded by the container's 768 MB, not by the heap); types from the bytes (never names), and libvips' loaders blocked but JPEG, PNG, WebP and GIF; a 40-megapixel limit read from the header; re-encoded to a fresh JPEG with no metadata. The server treats the worker as taken over by its input: it opens what the worker writes without following links or blocking (`O_NOFOLLOW`, `O_NONBLOCK`), regular files only, within a size cap; checks each result against the job's id and kind, with caps on characters, rows and cells; walks a returned JPEG's markers (no APPn, no COM, nothing after EOI, the frame the reported size); keeps one job in flight with a short queue (`busy` beyond it), so `work/in` never holds another person's file; and the worker skips a job nobody waits for any more (`@philobiblos/contracts/media`, `media/client.ts`). Captions marked untrusted in prompts |
| **A hostile video** (a share's MP4, MOV or WebM) | exploit a demuxer or decoder; make ffmpeg open another file or the network (an external data reference, a playlist, a concat list, a polyglot); exhaust CPU, memory or disk (an hour declared, or 5 s declared over an hour of frames, huge frames, a thousand streams); keep the sound or the video | only in the media worker, never in the server (an architecture test), under everything above, and: ffmpeg and ffprobe are FFmpeg's release built from source, pinned by SHA-256 (`Dockerfile`, `apps/worker/ffmpeg/build.sh`) with two demuxers (mov, matroska), four video decoders (H.264, HEVC, VP8, VP9: FFmpeg's own, no external library), no audio decoder, and one protocol, `fd`: no `file`, no network, so nothing in a file can name something to open (a test lists the build); the container from the bytes, and ffmpeg told which demuxer (`-f`), never probing; the input opened once per process by the worker (`O_NOFOLLOW`, a regular file, the same file each time, within 64 MB) and handed over as descriptor 3; the probe must name that container, at most 8 streams (the demuxer stops past 9: `-max_streams`), H.264/HEVC/VP8/VP9, at most 4096 pixels a side and 3840 × 2160 in all, at most 180 s (`too_long`); the decode reads no further than the duration said plus a second (`-t`), its decoder refuses larger frames (`-max_pixels`), the first video stream only (`-map 0:v:0`, `-an -sn -dn`), one thread, `-nostdin`, an empty environment; each process under `prlimit`: 50 CPU seconds, 512 MB of address space, no file it may write (`--fsize=0`), 16 descriptors, no core; a frame every 2 s (further apart past a minute), at most 30, scaled down to 1280 pixels a side, parsed as untrusted PPM (sizes, count, nothing half) and each re-encoded by sharp to a fresh JPEG of at most 2 MB; the result carries only the frames' sizes and offsets, checked field by field by the server, which walks each frame's JPEG markers as it does an image's; the video itself and its sound are never kept (the staged original is deleted once the worker answers). Fixtures: made at test time from ffmpeg's test sources (`apps/worker/test/video.test.ts`, CI `video`) |
| **A hostile PDF** | exploit pdfjs, exhaust memory | media worker; never in the server process (text only: no fonts, no eval, no XFA, no WebAssembly, images never decoded) |
| **A compromised or manipulated AI provider, prompt injection** (a caption, a book title from a mail or a PDF row, a blurb from a web page) | make Philobiblos act, fetch URLs, leak data, skew picks, run up costs | **Who is asked:** Ollama by default (nothing leaves the home network); Claude only after an admin's opt-in, in the same request as `acceptLeaves: true` after Settings showed the list of what leaves (`leavesWithClaude`, built from each job's `sends` fields, which `buildPrompt` enforces, null-valued keys included; `acceptLeaves` carries the `leavesVersion` the admin's page showed, refused when it is not the list as it is now; the accepted lines are stored, and a list holding a line they do not, a job turned on or a newer Philobiblos, pauses Claude until an admin accepts again); its key sealed like the delivery address, write-only (no route answers it, only `hasClaudeKey`), checked by its shape before sealing and never echoed; removing it turns the AI off. **Where to:** each AI call goes through an egress client whose whole allowlist is its provider's one host (`aiEgressRules`: the `OLLAMA_URL` host, or `api.anthropic.com` on https), a POST that is never redirected, at most 32 MB, its own deadline (180 s Ollama, 90 s Claude, 300 s at most); the general client for prices and metadata never carries AI requests. **What is sent:** each job's `split` (`packages/ai/src/jobs.ts`) picks the fields it needs, bounded (60 read books, 200 owned, 2,000 characters of blurb, 30 images); no person's name or the delivery address is in any job's input; takeaways only from `library/ai-context.ts`, only of those who turned `takeawaysToAi` on, and only with the run saying whose (`ai_run.takeaways_of`, the runner refuses otherwise), so what it proposes is private to them (`knowledge/from-run.ts`); images only the media worker's JPEGs, only to a model with vision. **How:** prompts are versioned files (`packages/ai/prompts/<job>.v<N>.md`, the version in every run and cache key); Philobiblos's own data (numbers, enums, its fixed lists) in an `<input>` block, every outside text and every idea name (a model may have proposed it) in an `<untrusted source=…>` block as JSON with `<`, `>` and `&` escaped, so nothing in it can close the block; no tools are ever offered (a tool call in an answer is no answer). **What comes back is data:** at most 64,000 characters, parsed as JSON, validated against `contracts/ai/<job>.schema.json`, cleaned by the job (an id only if the input named it, never the candidate's own; one line of plain text within its bound; whether an idea is new, how many suggestions, at most one wildcard and only when on, never an owned or backlog title: Philobiblos's decision, not the model's), every string through `safeField` (no piece of the delivery address, no run of 12 digits), validated again; invalid: tried once more, then the run fails and is logged without the answer's text; a stored answer is checked again before it is reused. **Never an effect:** output is stored as proposals and shown as text; a person's tap adds a book, confirms a link or takes a suggestion; an AI proposal counts in no brain or score until a person confirms it, whatever confidence the model gave (spec §6); a new idea name is kept on its proposal (`idea_proposal`) and becomes an idea only when a person confirms it (an architecture test: only `knowledge/from-run.ts` and the seed insert ideas), so a name an injected model made up never enters a later prompt's vocabulary; book ideas private to someone are left out of everyone else's runs (`resolvedTags` with the run's person), and a why built on something private to a pick's person is shown to them only (`order_line.why_audience`); scores come from `packages/scoring` only. **Cost:** a per-job-run budget of calls and tokens (60 calls, 400,000 tokens by default), each call's token limit, every call's cost and tokens in `ai_run`; with Claude a household allowance across every run (`ai_daily_tokens`, admins set it in Settings, 200,000 tokens in any 24 hours by default; `ai/spend.ts`): before each call the most it can cost (the prompt's UTF-8 bytes, a bound per image, its output limit) is reserved, and a call that could go past the allowance with what was spent and what other calls hold is not made, the job stopping as blocked; a failed call counts its bound; the runs a share starts may spend at most half the allowance per sharer and 40% per share token, so a leaked token cannot stop everyone's AI for the day; the AI reads at most 20 shares a day per share token and 40 per person, chosen fairly in SQL (round-robin by each person's oldest, within their caps, `ai/jobs.ts fairShares`), so one person's pile never hides another's shares; the rest wait. **The jobs** (`ai/jobs.ts`), each turned off in Settings by its switch and run by admins (`ai_suggest`, `ai_tag`, `ai_explain`) or after a share: a share's own images (kept JPEGs only, read without following links, path-checked), caption and link, for its sharer, into that share's found books; an adult backlog book's title, authors and blurb with the household's idea names, into proposed book ideas (a new idea is a name a person confirms; the book's audience and fiction flag are never changed); then, per adult whose backlog holds it, only their own read books (through `ai-context.ts`) into proposed links, private to them when their takeaways were read; the owned books in the same ideas into a proposed redundancy, which closes nothing until a person confirms it; an adult's reading map and the backlog's and shelf's titles into suggestions in their own Inbox only; a kept plan's adult picks into the one line of why This month shows |
| **A hostile or careless bookshop connector** (a connector file in the household's folder, a pull request, a later edit) | trust a forger's domain, reach a private host, make a parser hang, loosen a core rule (unsigned mail, redirects, sizes) | connectors are data (`contracts/connector.schema.json`, `connectors/load.ts`): plain YAML (no aliases, anchors, tags or duplicate keys), at most 64 KB, a plain file in a plain folder (no symbolic link), and every object refuses keys it does not name, so no connector can add a setting the core lacks; no code and no regular expression: its words are literals escaped into fixed, linear shapes (`connectors/text.ts`; tested on megabytes of hostile text); domains and hosts exact lowercase names (no address, wildcard, port or credentials); a quote sender only at its own mail domain; a signing domain aligned (same organizational domain) with one of its mail domains; no control or format characters in its words; the price URL https on 443 with the search words in its query string only; a household's own connector cannot take an id that ships. **It counts for nothing until enabled**: an admin reads in Settings what it allows (mail and signing domains, quote senders, its price host, its order address) and enables it with a sign-in of the last 10 minutes (standalone; under HomersLab refused until the edge's recent sign-in signal, ArjunRachithcf/homeward#253), naming the version (SHA-256 of the file) the page showed; a file that changes since allows nothing until enabled again; two enabled connectors never share a mail domain; the egress allowlist holds a shop's price host only while it is enabled, asked again at each request (`net/egress.ts`; HomersLab does not enforce per-host egress for connector hosts yet, ArjunRachithcf/homeward#255); every mail check above still applies to its mail. | **A malicious book page** (price lookup, Open Library) | oversized or script-laden pages, decompression bombs, redirects elsewhere | one HTTP client (`src/net/egress.ts`; an architecture test keeps every other connection out): allowlisted hosts by name, https only (Ollama on the home network the exception); resolved once, connected to the address checked, public hosts to public addresses only (no SSRF to the router, the edge or a neighbour container, no DNS rebinding); redirects on the same host only (at most 3), except covers: `archive.org` and `ia<number>.us.archive.org`, https on 443, at most 2 hops, each checked again; no compression; 1 MB JSON, 2 MB page, 5 MB image, 10 s for the whole exchange; the content type checked; an honest User-Agent and no cookies; pages parsed as text, Open Library's JSON field by field (a work key must look like one before it is followed); covers re-encoded by the media worker, never stored as fetched; `PHILOBIBLOS_EGRESS=off` turns it all off. | **The clock and the scheduler** (a restart mid-run, a clock set back or forward, a DST change, a run that hangs, two runs at once) | run a month's refresh twice (two plans, two pushes, suggestions twice), run an old month again, never stop retrying, run as someone | the monthly refresh (`jobs/schedule.ts`, `month/refresh.ts`) claims its period (the month in the household's zone) as a row, `job_period (job, period)`, in one immediate transaction: only once the household's day and time have come, never while another claim holds its lease (2 hours: longer than a run's 90-minute deadline plus the longest request), never after done or given up, and never when a later month has a row, so a clock set back runs no month again (a month missed while the server was off is not made up); every write of a claim names its attempt (a fencing token), so a claim that lost its lease changes nothing; in the process a job still running is never started again, by hand or by the clock, and each step runs in its own job's slot (never next to the same job by hand); a time the clocks skip runs as read with the old offset, one they repeat runs the first time; a failed run is tried again after 5 minutes, then 4 times longer each time, at most 5 times, then given up (logged; an admin can run it by hand, which takes no claim); the steps done are kept, so a retry repeats none of them; nothing new starts past the deadline, and the price lookup and the AI's loops check it too; after a restart a claim the old server held is free at once (one server per database, as `job_run`'s cleanup assumes); each run is in `job_run` with its period and each step's outcome in Philobiblos's words. ## Rules that follow

The rules are ADR 0009's. Each new route, connector or job states which actor it is exposed to and which control
applies; a feature that cannot meet them waits.

## Open points

- Web Push messages pass through the push services the browsers use (by default Google, Mozilla, Apple, Microsoft): they see when a
  device is told something and its encrypted message, never its text. Under HomersLab, its own notifications replace this
  when it has them (philobiblos#8).
- The scheduler assumes one Philobiblos server per database (as `job_run` does): a second server on the same database would
  wait for a claim's lease, but at its start it frees the claims the first one holds.
- One time zone: the household's (Settings). "This month" in the API, add_to_month, the plan's window and the monthly
  refresh all read it. `PHILOBIBLOS_TZ` is only its value when the settings row is made, at the first start; it is never read
  after. On an upgrade, a database whose settings row already exists keeps that row's zone (`Europe/Zurich`, the
  column's default, if budget or AI settings made the row), whatever `PHILOBIBLOS_TZ` says: an admin sets it in Settings.
  A zone is checked when it is written (Settings, `PHILOBIBLOS_TZ`); one this server does not know (written by hand, or an
  ICU update) stops the scheduler's ticks with a log line and a message in Settings, never the server.
- One currency: the household's (Settings; philobiblos#27). Every amount is in hundredths of it, and nothing is ever
  converted. None is assumed: `PHILOBIBLOS_CURRENCY` gives a household that has none its currency at a start (never
  replacing one it has), or an admin chooses it. A database from before M4 says the currency its amounts were in.
  A connector counts only in the household's currency: enabling one in another (or before there is one) is refused, one
  enabled before the currency changed underneath it counts for nothing (its senders, words and price host with it), and
  the currency does not change while a connector in another is enabled; a change removes every enabling, so a connector
  that counted for nothing never comes back into force by itself. A code is checked where it is written (the
  environment, Settings, a connector's file, the database's own CHECK) against the ISO 4217 codes the server knows.
- A clock that is wrong for a moment: the scheduler claims only the month it is now, and a row of this month counts
  whatever clock wrote it (a run minutes early or late is that month's run). A row for a later month does not stop the
  month it is now; it is made void (Settings shows "a run was recorded for a future month"), so that month runs again
  when it comes, except the push and the AI's steps, which happen once a period whatever clocks do. Attempts count
  per period across voids (5 at most). A period's retries stay in it: one that would fall into the next month gives up.
  The cost: a clock set back into a month that never ran runs that month once, and a month left behind by a clock set
  back across its end runs its mail, shares, prices and plan steps again (the plan kept stays as it was).
- The notification key (VAPID) is made only when none is sealed. A sealing key that does not open it is a wrong key, not
  a rotation: nothing is replaced and no device is removed, pushes stop (503, Settings → Notifications says so) until the
  right key is back. After a deliberate sealing-key change, an admin with a fresh sign-in makes a new notification key
  (Settings → Notifications, `DELETE /push/key`; under HomersLab refused until the edge's recent sign-in signal,
  ArjunRachithcf/homeward#253): the sealed key and every device go in one transaction, and each adult
  turns notifications on again (the page removes the browser's old subscription first).
- `PHILOBIBLOS_PUSH_HOSTS` checks wildcards for typos only, not against the Public Suffix List: three labels at least after
  `*.`, and a few public suffixes of three labels refused. Every send still goes to public addresses over https only.
- Compose copies the request to no one (no Bcc to Philobiblos's mailbox, which would then hold the address and whatever card
  number the person typed): a bookshop reply belongs to an order by its signed Subject ("Book order, <month>") or by
  the In-Reply-To of a bookshop mail already tied. A reply whose subject the bookshop rewrites goes to the Inbox
  unmatched.
- The parsers' layouts are written from `contracts/connectors.md`, with invented fixtures. Real mails may differ (an
  online order's line, an invoice's cells); they then fail closed as `unknown_layout` until a parser version reads
  them. A private test against real mails kept outside the repository can confirm the layouts.

- The media worker has no seccomp profile beyond Docker's default, and no Landlock; ffmpeg and ffprobe run under `prlimit` (address space, CPU, no files), the Node child does not (the container's memory limit is its bound).
- AV1 video is refused: FFmpeg's only software AV1 decoder is an external library (dav1d), which the build leaves out. Phones send H.264 or HEVC; a browser's recording is VP8 or VP9.
- A crafted file of many tiny packets (Matroska lacing, say) is not capped by count: FFmpeg's command line has no packet limit, so the 60 s wall clock and the CPU limit are its bound (a 21 MB lace bomb costs about 30 s of the worker).
- A 3-minute 4K video takes longer to decode than the 60 s a video gets on one core, and times out; 1080p fits (a 60 s reel decodes in under 10 s).
- A video takes up to 60 s of the worker, which runs one job at a time: a share of several long videos waits behind itself. A video over 180 s is refused (`too_long`): trim it first.
- Whether the HomersLab proxy authenticates itself to Philobiblos with more than its address (mTLS, a shared secret) depends
  on HomersLab's feedstock format. Until then the address is trusted only because HomersLab ADR 0020's firewall keeps
  everything but the edge off Philobiblos's port.
- A location rule is as narrow as the network an admin lists: a guest network on the same range counts as home. Behind
  a reverse proxy that is not `PHILOBIBLOS_TRUSTED_PROXY`, every client has the proxy's address, so a rule on the home
  network would match everyone the proxy serves. Under HomersLab the rule waits for the edge to say a request came over
  the mesh (ADR 0011, ArjunRachithcf/homeward#252).
- A mail-domain rule trusts whoever controls addresses at that domain; a domain with addresses for outsiders (a
  school's, an employer's) lets them in as adults. Settings says so when the rule is set.
- Sign-in rate limits count per client address. Behind a reverse proxy every client has the proxy's address, so the
  limit is shared by the household (20 sign-in steps a minute); a proxy in front of standalone Philobiblos should keep its
  own limits.

## Rotating the sealing key

There is no re-encryption step, on purpose: Philobiblos never holds two keys. To rotate (or after a key is lost):

1. Replace the key: a new `PHILOBIBLOS_SEALING_KEY` under HomersLab; standalone, delete `keys/sealing.key` (a new one is
   made on the next save).
2. Settings keeps working for everyone; "Where orders go" says the addresses need entering again (`needsReentry`), and
   Compose answers 409 until they are.
3. An admin enters the bookshop's address and the delivery address again; they are sealed under the new key.

The old rows cannot be opened with the new key (each row carries its key's id, and GCM refuses anything else).

## The rename from Shelf

The app was called Shelf until 2026-11-16 (philobiblos#30). What carries over, for one release (every 0.1.x; 0.2.0 drops
it, and `apps/server/test/env.test.ts` fails once the version says 0.2):

- **Settings**: a `SHELF_*` variable is read as its `PHILOBIBLOS_*` name (`packages/contracts/src/env.ts`), with one
  warning per process that names the variables and never their values; when both are set the `PHILOBIBLOS_*` one wins
  and the warning says the other was ignored. An empty value counts as unset, so it never hides an old name or an
  image default, and an empty `PHILOBIBLOS_DATA_DIR`, `PHILOBIBLOS_DB_FILE` or `PHILOBIBLOS_KEYS_DIR` is refused
  (`''` would be the working folder or an in-memory database). The names that set one thing together are one setting
  (the data folder and database file, the sealing key and its file, the IMAP password and its file): once a new name of
  a setting is set, its old names are all ignored, so old and new never mix. docker-compose.yml reads a `.env`'s `SHELF_*` the same way. The image's
  defaults (`/data`, `/keys`, `/work`, `0.0.0.0:8080`) are applied after the old names, never as the Dockerfile's `ENV`:
  an `ENV PHILOBIBLOS_DATA_DIR=/data` would win over a household's `SHELF_DATA_DIR` and open an empty database elsewhere.
- **Session cookie**: `shelf_session` is still read when `philobiblos_session` is absent (never when it is there, even
  dead), with the same check (its SHA-256 must be a live session row). The first request that brings it gets
  `philobiblos_session` with the same token, the same attributes and only what is left of the session, and
  `shelf_session` cleared (it is cleared whenever it comes, also next to the new one); sign-in and sign-out end and
  clear both. Nobody is signed out by the upgrade, and no session
  lives longer than it would have.
- **Passkeys**: the WebAuthn RP name is now Philobiblos; the RP ID is still the origin's host, which is what a passkey is
  bound to, so every passkey keeps working at the same address.
- **What leaves for Claude**: an admin's acceptance of the lines that named Shelf still holds for the same lines naming
  Philobiblos (`ai/settings.ts`); any other change still needs a new acceptance.
- **The command**: `shelf` in the image still runs `philobiblos`, with a warning.
- **Kept as they are**, so nothing moves: the data folder and its files (`data/shelf.sqlite`, `keys/sealing.key`,
  `work/`); the phone share's service-worker cache `shelf-share` and its `x-shelf-*` headers (an old service worker
  may still be the one running when the new page loads); the HomersLab headers `X-HomersLab-*` (the umbrella's name).
  Renaming the database file would need a migration step at start (move, then open), never a silent move.
- **Compose**: the services are now `philobiblos` and `philobiblos-worker`; start the new file with
  `docker compose up -d --remove-orphans` so the old `shelf` containers stop (two servers or two workers must never
  share `data/` and `work/`).
